Over the last few months I wrote several posts about how I work around software development: how I organize my local environment, how I work with Git and GitHub, and how I use AI tools as part of the development process rather than as a replacement for it.

In the post about [running VS Code, WSL, Conda, and unittest](https://www.sagiv-barhoom.me/python/2026/02/13/vscode_wsl_conda_unittest_setup.html), I focused on the local development environment. In the post about a [Git workflow for CSM Researchers](https://www.sagiv-barhoom.me/github/2026/02/06/Git_Workflow_CSM_Researchers.html), I described a structured process around branches, commits, and pull requests. Later, in the post about [Codex CLI with Git worktree and Docker Compose](https://www.sagiv-barhoom.me/codex/2026/05/08/codex-cli-git-worktree-docker-compose.html), I went into a more practical setup for using AI tools inside an isolated development environment.

After a few rounds of working this way, especially with changes generated by AI or delivered as ZIP files, another recurring layer became clear. It was not the local environment itself, and not only the code. It was the layer that manages the lifecycle of a change: starting from a clean branch, applying the change in the right place, understanding what changed, running tests, creating a precise commit, opening a PR, merging, syncing `main`, cleaning up branches, and sometimes creating a tag.

Each step is simple on its own. The problem is that the full sequence repeats again and again, and every repetition leaves enough room for a small mistake to enter the process.

## The problem was not Git

The problem was not lack of Git knowledge.

I knew how to run the commands manually. The problem was that every task required remembering the same sequence again, in the same order, with the same checks in between.

For example:

- Make sure I am not working directly on `main`
- Make sure the working tree is clean before starting
- Avoid creating a new branch while an untracked ZIP file is sitting at the repository root
- Avoid creating a PR before there is a real commit
- Avoid deleting a branch before the merge was pulled into local `main`
- Avoid creating a tag before the relevant PR was actually merged

These are not complex problems. They are exactly the kind of problems that are easy to miss when working quickly, switching between projects, or applying changes received from an external process.

## The pattern that kept repeating

After a few rounds, the pattern became clear:

```text
prepare -> change -> review -> test -> commit -> PR -> merge -> cleanup -> tag
```

In practice, it looked roughly like this:

```text
1. Make sure main is up to date and clean
2. Create a dedicated branch for the task
3. Apply a ZIP file or make a manual change
4. Review the changes
5. Run tests
6. Create a controlled commit
7. Push the branch and open a PR
8. Merge through GitHub
9. Sync local main
10. Clean up branches
11. Create a tag for a stable version
```

This is the basis for `ai-git-workflow-tools`.

[https://github.com/sagivba/ai-git-workflow-tools](https://github.com/sagivba/ai-git-workflow-tools)

I did not want a tool that hides Git. I wanted a tool that holds the process around Git.

## What the tool does

`ai-git-workflow-tools` is a set of Bash functions for repeated work around Git, GitHub, and changes that come from an AI-assisted workflow or from ZIP files.

It does not try to replace Git, and it does not try to merge automatically. Its purpose is to help me run the same workflow consistently, with checkpoints and validations that prevent simple mistakes.

The main principles are:

- `dry-run` by default
- A separate branch for each task
- Preventing some operations directly on `main`
- Checking the working tree before sensitive operations
- Committing only explicit files
- Keeping GitHub as the place where merge happens
- Running cleanup and tag creation only after a proper merge and sync

## Dry-run by default

Every operation that can change Git state first prints what it is going to do.

Only when I add `--run` does the operation actually execute.

For example:

```bash
agw_start_task --task T008 --slug some-task
```

```bash
# git fetch --prune origin && git switch main && git pull --ff-only origin main && git status --short && git log --oneline --decorate -5 && git switch -c manual/T008-some-task
```

This command does not actually create a branch, because I did not add `--run`. It only prints the sequence of commands the tool would run in execution mode.

In this case, behind the scenes, the tool builds a branch name from two parts:

```text
manual/T008-some-task
```

Then it plans to run a sequence like this:

```bash
git fetch --prune origin
git switch main
git pull --ff-only origin main
git status --short
git log --oneline --decorate -5
git switch -c manual/T008-some-task
```

In `--run` mode, before creating the branch, the tool also checks that the working tree is clean and that a local or remote branch with the same name does not already exist. If one of the checks fails, the operation stops.

To execute it for real:

```bash
agw_start_task --task T008 --slug some-task --run
```

```bash
# git fetch --prune origin && git switch main && git pull --ff-only origin main && test -z "$(git status --short)" && git show-ref --verify --quiet refs/heads/manual/T008-some-task || true && git switch -c manual/T008-some-task
```

> Note: a `slug` is a short, readable name that is safe to use in a branch name or URL. Instead of a sentence with spaces and special characters, it uses lowercase letters, numbers, and hyphens. For example, `Update README examples` becomes `update-readme-examples`.

The `slug` is the short readable part of the branch name. In this case, `some-task`. It briefly describes the task using lowercase letters, numbers, and hyphens.

For example:

```bash
agw_start_task --task T012 --slug update-readme-examples --run
```

```bash
# git fetch --prune origin && git switch main && git pull --ff-only origin main && test -z "$(git status --short)" && git switch -c manual/T012-update-readme-examples
```

Will create a branch named:

```text
manual/T012-update-readme-examples
```

I use a `slug` when I have a task number or work identifier, but still want a branch name that is easy to understand when reading `git branch`, GitHub, or a list of PRs. The number gives traceability, and the slug gives human context.

This sounds like a small detail, but in practice it is one of the most important parts of the tool. I want to see the operation before it changes the repository.

## A branch for each task

The tool encourages working in a dedicated branch for every change.

The naming pattern I use is:

```text
manual/T<number>-short-slug
```

For example:

```text
manual/T008-some-task
```

Creating a branch is done like this:

```bash
agw_start_task --task T008 --slug some-task --run
```

```bash
# git fetch --prune origin && git switch main && git pull --ff-only origin main && test -z "$(git status --short)" && git switch -c manual/T008-some-task
```

Before creating the branch, the tool checks that the repository is in a suitable state: that the repository is where I expect it to be, that the working tree is clean, and that I am not starting a new task on top of an unclear state.

## Clean working tree before starting

One thing that happened repeatedly was a ZIP file sitting at the root of the repository.

From Git’s perspective, that is an `untracked file`. Even if the file is only temporary input for the task, it still makes the working tree dirty.

So before starting a task, I move it out of the repository, for example:

```bash
mkdir -p /tmp/agw-zips
mv T008-some-task.zip /tmp/agw-zips/
```

```bash
# mkdir -p /tmp/agw-zips && mv T008-some-task.zip /tmp/agw-zips/
```

This is not a new idea introduced by the tool. It is simply a check that the tool forces me not to skip.

## Controlled commit

One of the easiest mistakes is to run:

```bash
git add .
```

In a small project this sometimes works fine. But when working with files extracted from a ZIP, temporary outputs, or changes generated by AI, I prefer to be explicit.

So the tool provides a commit function where the files are listed explicitly:

```bash
agw_commit_controlled_change \
  --message "Describe the change" \
  --files "file1 file2" \
  --run
```

```bash
# git status --short && git add file1 file2 && git diff --cached --stat && git commit -m "Describe the change"
```

The goal is not to save typing. The goal is to avoid accidentally including unrelated files in the commit.

## A basic workflow example

A basic workflow looks like this, but it is important to understand what each command actually does.

Load the tool functions into the current shell:

```bash
source scripts/load-agw.sh
```

```bash
# test -f scripts/load-agw.sh && source scripts/load-agw.sh
```

This command does not change the repository. It only loads the functions and lets the tool know where it was loaded from and which repository is the current one.

After loading, check the tool and repository state:

```bash
agw_status
```

```bash
# agw_version && pwd && git rev-parse --show-toplevel && git branch --show-current && git status --short
```

This prints basic information such as the tool version, the path it was loaded from, and the current repository. It helps verify that the tool is operating on the correct project, not accidentally on the tool repository itself or another directory.

Create a new branch for the task:

```bash
agw_start_task --task T008 --slug some-task --run
```

```bash
# git fetch --prune origin && git switch main && git pull --ff-only origin main && test -z "$(git status --short)" && git switch -c manual/T008-some-task
```

In practice, the command checks that the working tree is clean, makes sure I am not starting from an unclear state, and creates a predictable branch name, for example:

```text
manual/T008-some-task
```

Without `--run`, the tool only prints the expected operations. With `--run`, it executes them.

At this point I apply the actual change. It can be a manual edit, code generated by AI, or files extracted from a ZIP:

```bash
# apply changes manually or unzip task files
```

```bash
# unzip /tmp/T008-some-task.zip -d . && git status --short
```

After the change is in the repository, review what changed:

```bash
agw_review_output --run
```

```bash
# git status --short && git diff --stat && git diff
```

This command groups the first checks around the change. In practice, it is meant to show the Git state and the diff, so I can understand which files changed before moving on to a commit.

Then run the project tests:

```bash
make test
```

```bash
# make test
```

This is not a tool command. It is the project’s validation point. In another project it might be `pytest`, `npm test`, or any other local test command.

Only after review and tests do I create a controlled commit:

```bash
agw_commit_controlled_change \
  --message "Describe the change" \
  --files "file1 file2" \
  --run
```

```bash
# git status --short && git add file1 file2 && git diff --cached --stat && git commit -m "Describe the change"
```

Instead of running `git add .`, the command receives an explicit list of files through `--files`. In practice, it stages only those files, creates a commit with the provided message, and avoids adding unrelated files by mistake.

Then create a PR body, for example:

```bash
cat > /tmp/T008-pr-body.md <<'EOF'
## Summary

- Describe the change.

## Validation

- `make test`
EOF
```

```bash
# cat > /tmp/T008-pr-body.md <<'EOF' && test -s /tmp/T008-pr-body.md
```

This is also not a tool command. It is just a temporary text file that will be used as the Pull Request body. I prefer creating it as a file so I can read and edit it before opening the PR.

Then push the branch and open a PR:

```bash
agw_push_and_pr \
  --title "T008 Describe the change" \
  --body-file /tmp/T008-pr-body.md \
  --run
```

```bash
# git push -u origin HEAD && gh pr create --title "T008 Describe the change" --body-file /tmp/T008-pr-body.md
```

In practice, the command pushes the branch to the remote and then uses the GitHub CLI to open a Pull Request with the provided title and body. Here too, without `--run`, it prints the expected commands and does not execute them.

The merge itself still happens through GitHub.

That is intentional. I do not want the tool to merge automatically. The PR is the last checkpoint before the change enters `main`.

## After merge

After the PR is merged through GitHub, sync local `main`:

```bash
agw_post_merge_sync --run
```

```bash
# git switch main && git pull --ff-only origin main && git log --oneline --decorate -5
```

Then clean up branches:

```bash
agw_cleanup_branches --branch manual/T008-some-task --run
agw_cleanup_branches --branch manual/T008-some-task --remote --run
```

```bash
# git branch --merged main | grep manual/T008-some-task && git branch -d manual/T008-some-task && git push origin --delete manual/T008-some-task
```

Only after the merge and sync are complete, create a tag:

```bash
agw_create_tag --tag v0.7.0 --note "Describe the change" --run
```

```bash
# git switch main && git pull --ff-only origin main && git rev-parse v0.7.0 >/dev/null 2>&1 || git tag -a v0.7.0 -m "Describe the change" && git push origin v0.7.0
```

Here too, the tool is not trying to be clever. It simply keeps the order correct.

## Using the tool from another project

One important point for me was that the tool should be loadable from one place, while operating on the project I am currently in.

For example:

```bash
source tools/ai-git-workflow-tools/scripts/load-agw.sh
agw_status
```

```bash
# test -f tools/ai-git-workflow-tools/scripts/load-agw.sh && source tools/ai-git-workflow-tools/scripts/load-agw.sh && agw_version && git rev-parse --show-toplevel && git status --short
```

The status output shows both where the tool was loaded from and the current repository on which the commands operate.

This matters because I do not want to confuse the tool repository with the repository I am actually working on.

There are two simple ways to integrate it into another project.

Using a submodule:

```bash
git submodule add https://github.com/sagivba/ai-git-workflow-tools.git tools/ai-git-workflow-tools
cd tools/ai-git-workflow-tools
git checkout v0.6.0
cd ../..
source tools/ai-git-workflow-tools/scripts/load-agw.sh
```

```bash
# git submodule add https://github.com/sagivba/ai-git-workflow-tools.git tools/ai-git-workflow-tools && cd tools/ai-git-workflow-tools && git checkout v0.6.0 && cd ../.. && source tools/ai-git-workflow-tools/scripts/load-agw.sh
```

Or by copying the files:

```bash
mkdir -p tools/ai-git-workflow-tools/scripts

cp ~/src/ai-git-workflow-tools/scripts/ai-git-workflows.sh \
  tools/ai-git-workflow-tools/scripts/

cp ~/src/ai-git-workflow-tools/scripts/load-agw.sh \
  tools/ai-git-workflow-tools/scripts/

source tools/ai-git-workflow-tools/scripts/load-agw.sh
```

```bash
# mkdir -p tools/ai-git-workflow-tools/scripts && cp ~/src/ai-git-workflow-tools/scripts/ai-git-workflows.sh tools/ai-git-workflow-tools/scripts/ && cp ~/src/ai-git-workflow-tools/scripts/load-agw.sh tools/ai-git-workflow-tools/scripts/ && source tools/ai-git-workflow-tools/scripts/load-agw.sh
```

## Why not full automation

The tool was not built to hide the process.

It was built to make it clearer.

That is why there are several things it intentionally does not do:

- It does not run `git add .`
- It does not merge PRs automatically
- It does not create a tag before the merge is complete
- It does not delete a branch that was not merged
- It does not run a state-changing operation without `--run`

In this case, guardrails matter more than full automation.

I still want to see the diff. I still want to run tests. I still want the merge to be a deliberate action through GitHub.

The tool only makes sure I do not skip steps that repeated enough times to justify an automatic check.

## Current state

`ai-git-workflow-tools` is currently a personal workflow tool that reached a useful state.

It is not a complete distribution-ready product, and not a general-purpose CLI library. It was built from a real workflow, and it mostly fits people who work in a similar way: one branch per task, PRs through GitHub, manual merge, cleanup, and sometimes a tag at the end of the workflow.

The project is here:

```text
https://github.com/sagivba/ai-git-workflow-tools
```

Future development will probably come from using it in more real projects, not from planning more features up front.
